# REQ-005: check-toc（ToC 鮮度確認）要件定義書

## 概要

`check-toc` は、指定 key の ToC が **そのまま検索に使えるか（`fresh`） / 作り直しが必要か（`stale`）** を返す
read-only な SKILL である。判定結果を機械可読な JSON として返すことだけを行い、索引の生成・更新・削除は一切行わない。

ToC が存在しない場合も `stale` に含める。不在と鮮度超過は、呼び出し側の後続処理（索引の作り直し）が同一だからである。
両者の区別は、答えとは別の補助情報（`reason`）として返し、情報を落とさない。

上位層（forge 等）が「検索前に索引を作り直すべきか」を判断するための材料を提供する。
判断そのもの（鮮度閾値をいくつにするか、古いときに何をするか）は上位層の責務であり、本 SKILL は持たない。

## 背景とスコープ

| 項目       | 内容                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------- |
| 出典       | 上位層（forge）の文書検索 wrapper が、doc-advisor 経路へ切り替える前に ToC の鮮度を確認する要求 |
| 適用ルール | `docs/rules/document_writing_rules.md` / `docs/rules/implementation_guidelines.md`              |
| 関連       | REQ-001（key 単位 ToC 管理・opaque key）、DES-005（ToC 生成フローと `metadata.generated_at`）   |

### 対象

- 指定 key の ToC の存在確認
- 与えられた鮮度閾値に対する新旧判定
- 判定結果の JSON 出力

### 対象外

- ToC の生成・更新・削除（`index-docs` / `remove-toc` の責務）
- 鮮度閾値の決定（呼び出し側が渡す）
- 古い ToC を検出したときの索引更新の起動
- 検索の実行（`query-docs` の責務）
- ToC の内容（`docs` エントリ）の返却（`get_toc.py` の責務）

## 前提条件

| ID      | 前提                                                                                         |
| ------- | -------------------------------------------------------------------------------------------- |
| PRE-C01 | ToC の `metadata.generated_at` は ToC 生成時に UTC の ISO 8601 として書かれている（DES-005） |
| PRE-C02 | key から保存パスへの変換は既存の決定的変換を用いる（REQ-001 FR-N01-3）                       |
| PRE-C03 | 呼び出し側は鮮度閾値を秒の整数で渡す。単位付き表記の解析は本 SKILL の責務に含めない          |

## 機能要件

### FR-C01 入力

| ID       | 要件                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| FR-C01-1 | `--key <key>` で対象 ToC を指定する。key は不透明文字列として扱い、値域を列挙しない              |
| FR-C01-2 | `--all`（または `--key` 省略）は予約 key `all` に解決する。既存 script と同じ key 解決規則に従う |
| FR-C01-3 | `--max-age <秒>` を必須とする。正の整数以外は入力エラーとする                                    |
| FR-C01-4 | 上記以外の引数を受け取らない。閾値の既定値を本 SKILL 側に持たない                                |

`--max-age` を必須にするのは、閾値の所有者を呼び出し側に固定するためである。
既定値を持つと、呼び出し側が閾値を渡し忘れた場合に本 SKILL の既定値が暗黙の方針として作用する。

### FR-C02 判定規則

| ID       | 状態                                                  | `freshness` | `reason`               |
| -------- | ----------------------------------------------------- | ----------- | ---------------------- |
| FR-C02-1 | 当該 key の `toc.yaml` が存在しない                   | `stale`     | `missing`              |
| FR-C02-2 | `generated_at` が欠落している、または解析できない     | `stale`     | `generated_at_invalid` |
| FR-C02-3 | `generated_at` が許容 skew を超えて未来を指している   | `stale`     | `generated_at_future`  |
| FR-C02-4 | 判定時刻と `generated_at` の差が `--max-age` 以下     | `fresh`     | `null`                 |
| FR-C02-5 | 判定時刻と `generated_at` の差が `--max-age` を超える | `stale`     | `outdated`             |

- 境界値（差が `--max-age` と等しい）は `fresh` とする。
- `freshness` は `fresh` / `stale` の 2 値とする。ToC 不在を独立の値として返さないのは、呼び出し側の後続処理が
  鮮度超過と同一であり、答えの値域を増やす利得がないためである。
- 不在・鮮度超過・`generated_at` 不正の区別は `reason` で返す。`reason` は診断用の補助情報であり、
  呼び出し側が分岐に使うことを前提としない。`reason` を読まなくても後続処理は `freshness` だけで決まる。
- 鮮度の根拠は `metadata.generated_at` だけとする。ファイルの mtime を根拠にしない。
- `.toc_work/` の pending 有無・lease 状態は判定に用いない。判定対象は `toc.yaml` のみである。

### FR-C03 出力

| ID       | 要件                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| FR-C03-1 | 判定結果を JSON で stdout に出力する。既存 script と同じく `status` と `error_code` を必須とする |
| FR-C03-2 | 本 SKILL が返す `status` は `ok` と `error` の 2 値のみとする                                    |
| FR-C03-3 | ToC 不在は `status=ok` / `freshness=stale` / `reason=missing` とし、`error_code` を設定しない    |
| FR-C03-4 | SKILL の最終出力は script の JSON のみとし、前後に説明文・要約を付けない                         |

| field             | 内容                                                                |
| ----------------- | ------------------------------------------------------------------- |
| `status`          | `ok`（判定完了） / `error`（判定不能）                              |
| `error_code`      | `status=error` のときの理由コード。`status=ok` では `null`          |
| `key`             | 解決後の key                                                        |
| `toc_path`        | `toc.yaml` の project-root 相対パス（不在時も期待パスを返す）       |
| `freshness`       | `fresh` / `stale`。`status=error` では `null`                       |
| `reason`          | `stale` の原因（FR-C02）。`fresh` および `status=error` では `null` |
| `generated_at`    | ToC の `metadata.generated_at`。不在・欠落・解析不能では `null`     |
| `age_seconds`     | 判定時刻と `generated_at` の差（秒）。算出できない場合は `null`     |
| `max_age_seconds` | 入力された閾値のエコー                                              |

ToC 不在を `error` としないのは、本 SKILL の目的が存在確認そのものだからである。
ToC の内容取得を目的とする `get_toc.py` では不在は目的達成の不能（`TOC_NOT_FOUND`）だが、
本 SKILL では不在は正常な判定結果である。この差は意図的なものであり、既存慣行を継がない。

exit code は `status=ok` で `0`、`status=error` で `1` とする。`freshness` の値は exit code に反映しない。

### FR-C04 SKILL としての公開

| ID       | 要件                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| FR-C04-1 | 配布 SKILL として公開する。上位層が available-skills 上の存在を可用性判定の根拠に使うため |
| FR-C04-2 | 決定論的な判定処理は script に置き、SKILL は薄いラッパとする                              |
| FR-C04-3 | 副作用を持たない。ToC・`.toc_work/`・checksums のいずれも書き換えない                     |

## 非機能要件

| ID      | 要件                                                                                         |
| ------- | -------------------------------------------------------------------------------------------- |
| NFR-C01 | Python 標準ライブラリのみで実装する（NFR-003）                                               |
| NFR-C02 | 判定は `toc.yaml` の metadata 部分の読み取りだけで完了させる。全エントリの解析を必要としない |
| NFR-C03 | 判定時刻は差し替え可能な境界とし、単体テストが実時刻に依存しないようにする                   |
| NFR-C04 | 出力に絶対パス・環境変数値・設定本文を含めない。パスは project-root 相対で返す               |

## エラーケース

| 条件                                     | 動作                                      |
| ---------------------------------------- | ----------------------------------------- |
| `--max-age` が未指定・非整数・0 以下     | `status=error`。判定を行わない            |
| key が空、または予約語 `all` を明示指定  | 既存の key 検証と同じ `error_code` で失敗 |
| ToC store を読み取れない（権限・破損等） | `status=error`。`freshness` は返さない    |
| `toc.yaml` が存在しない                  | `status=ok` / `freshness=stale`（正常）   |

## 呼び出し側への影響

- 答えは `fresh` / `stale` の 2 値であり、ToC 不在は `stale` に含まれる。呼び出し側は不在専用の分岐を持たなくてよい。
- 本 SKILL は鮮度閾値を持たないため、呼び出し側が毎回 `--max-age` を渡す。
- 本 SKILL は索引を更新しないため、`stale` を受けた後の索引更新は呼び出し側が `index-docs` を起動して行う。
- 境界値の扱い・skew の許容幅・`generated_at` の解釈・ToC の探索方法は本 SKILL の内部判断であり、呼び出し側は依存しない。
