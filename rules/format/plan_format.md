# 計画書フォーマットルール

## 目的

要件定義から設計、実装までの全工程で要件を追跡可能にし、以下を実現します：

- **要件と実装の紐付け**: すべての要件がどのファイルで実装されているか明確化
- **影響範囲の明確化**: 要件変更時の影響箇所を即座に特定
- **タスクベース開発**: 各タスクが要件と紐付き、Agentによる自動実装が可能

## ID体系

### 要件ID

要件IDの体系と命名規則は[要件定義書フォーマットルール](spec_format.md#要件ID体系)に定義されています。

**要件IDプレフィックス**（完全版）：

- **APP-**: アプリケーション全体概要 (Application Overview) ※最上位要件
- **SCR-**: 画面要件 (Screens)
- **CMP-**: UIコンポーネント (Components)
- **FNC-**: 機能要件 (Functions)
- **BL-**: ビジネスロジック (Business Logic)
- **NF-**: 非機能要件 (Non-Functional)
- **DM-**: データモデル (Data Models)
- **EXT-**: 外部インターフェース (External Interfaces)
- **NAV-**: ナビゲーション要件 (Navigation)
- **THEME-**: デザイントークン・テーマ要件 (Theme)
- **BUG-**: バグ報告・不具合修正 (Bug Fix)

**注**: 上記の全てが `specs/{feature}/requirements/` のチェック対象となる。

### 設計ID

- **DES-**: 設計書 (Design Documents)
- 連番形式：DES-001, DES-002, DES-003...

## ワークフロー間でのID活用

```
1. 要件定義フェーズ (import_app_workflow.md / import_figma_workflow.md)
   ↓ 要件IDを付与（例: SCR-001）
   
2. 設計フェーズ (design_workflow.md)
   ↓ 要件IDを参照して設計
   ↓ 設計IDを付与（例: DES-001）
   
3. 計画フェーズ (planning_workflow.md)
   ↓ 要件トレーサビリティマトリクス作成（要件ID → 設計ID）
   ↓ 設計トレーサビリティマトリクス作成（設計ID → タスクID）
   ↓ タスク一覧作成
   
4. 実装フェーズ (task_execution_workflow.md)
   ↓ タスク単位でAgent実行（設計書を参照）
   
5. 完了確認
   タスクのチェックマークで進捗確認
```

## 計画書の構成 [MANDATORY]

計画書（`specs/{feature}/plan/{feature}_plan.md`）は以下のセクションで構成されます：

1. **要件トレーサビリティマトリクス** - 要件IDから設計IDへの対応
2. **設計トレーサビリティマトリクス** - 設計IDからタスクIDへの対応
3. **タスク一覧** - 実装タスクの詳細
4. **改定履歴** - 計画書の変更履歴

**上記以外のセクションは追加しないこと。** 計画書の目的は「優先度の高いタスクを検出し実行する」ことであり、タスク実行に不要な情報（依存関係図、概要説明等）は記載しない。タスク実行に必要な情報はすべてタスク表の各列（設計ID、依存関係、必読等）に含める。

## 要件トレーサビリティマトリクス

要件IDから設計IDへの対応を管理します。

### マトリクス構造

```markdown
| ✓  | 要件ID  | タイトル           | 内容                               | 設計ID         |
| -- | ------- | ------------------ | ---------------------------------- | -------------- |
| ✅ | APP-001 | アプリ全体概要     | {アプリ名}の基本仕様               | -              |
| ✅ | SCR-001 | アイテム一覧画面   | メイン画面、カテゴリサイドバー付き | DES-001        |
| ☐  | FNC-001 | カテゴリ管理       | カテゴリの作成・編集・削除機能     | 設計書作成待ち |
| ✅ | BL-001  | データ同期・永続化 | アイテムデータの同期と保存         | DES-001        |
```

### 各列の説明

- **✓**: 設計書作成状態（✅完了、☐未完了）
- **要件ID**: 要件定義書で付与された一意のID
- **タイトル**: 要件の日本語タイトル
- **内容**: 要件の簡潔な説明
- **設計ID**: 対応する設計書のID（複数可、APP-001のような最上位要件は設計書なしで「-」、未作成時は「設計書作成待ち」）

## 設計トレーサビリティマトリクス

設計IDからタスクIDへの対応を管理します。

### マトリクス構造

```markdown
| 設計ID  | タイトル         | 内容                                     | 要件ID                            | タスクID                                   |
| ------- | ---------------- | ---------------------------------------- | --------------------------------- | ------------------------------------------ |
| DES-001 | アイテム一覧設計 | アイテム一覧表示とカテゴリフィルタリング | SCR-001, CMP-001                  | D-001〜D-008, UI-001〜UI-005, I-001〜I-006 |
| DES-002 | 詳細画面設計     | アイテム詳細表示とアクション実行         | SCR-003, CMP-002, BL-004          | D-009〜D-013, UI-006〜UI-011, I-007〜I-011 |
| DES-003 | 設定画面設計     | アプリ設定とカテゴリ管理                 | SCR-006, SCR-009, SCR-005, BL-003 | D-014〜D-018, UI-012〜UI-018, I-012〜I-015 |
```

### 各列の説明

- **設計ID**: 設計書の一意のID
- **タイトル**: 設計書の日本語タイトル
- **内容**: 設計の簡潔な説明
- **要件ID**: 関連する要件ID（複数可）
- **タスクID**: 生成されるタスクID（複数可、範囲表記可）

### TDD対応タスク順序 [MANDATORY]

Domain層Serviceの実装は、以下の順序でタスクを実行する：

#### 新規Service実装の場合

```
1. Entity/Enum/ValueObject定義（優先度57）
2. DataStore/Repository Protocol定義（優先度57）
3. DataStoreMock/RepositoryMock実装（優先度56）
4. Unit Test作成（優先度56）← テストを先に作成
5. Service実装（優先度55）← テストを通す実装
6. リファクタリング（優先度53）← テスト通過後の整理
```

#### 既存Service修正の場合

```
1. Unit Test追加（現在の振る舞いを確認するテストを作成）
2. Service修正
3. テスト確認
```

**重要**: Unit TestはService実装より**先に**作成する。これにより、期待する振る舞いを明確に定義してから実装に取り掛かることができる。

### タスクの粒度

タスクは以下の基準で分割します：

1. **1つのAgent実行で完結する単位**
   - 1つのService、1つのView/ViewModel、1つのDataStore実装など
   - 対応するMock実装（DataStoreMock、RepositoryMock等）は別タスクとして分割（※ServiceのMockは作成しない。`coding_rule.md` 参照）
   - 複数のViewやServiceを1タスクにまとめない

2. **独立して実装・テスト可能な単位**
   - 他のタスクの完了を待たずに着手できる
   - **独立タスクの場合**: タスク完了時にビルド・テストが成功すること [MANDATORY]
   - **タスクグループの場合**: グループ全体完了時にビルド・テストが成功すること [MANDATORY]
   - グループ途中タスクはビルドエラーを許容（詳細は「タスクグループ」セクション参照）

3. **目安となる規模**
   - 1つのファイル、または密接に関連する2〜３つのファイル（View/ViewModel等）
   - やるべき内容は5〜10項目程度に抑える

4. **粒度の例**
   - ✅ 良い例：XXXXXService実装、XXXXXListView実装、XXXXXDataStoreImpl実装、XXXXXDataStoreMock実装、XXXXXRepositoryMock実装
   - ❌ 悪い例：全Service実装、全画面実装、Domain層全体実装、ServiceMock作成（ServiceのMockは作成しない）

### タスクグループ [MANDATORY]

#### 概要

複数ファイルの同期変更が技術的に必須の場合、複数タスクを1つのグループとして扱います。

#### グループ化が必要なケース

以下のいずれかに該当する場合、タスクグループ化を検討します：

1. **インターフェース変更**
   - メソッドシグネチャの変更
   - Protocol定義の変更
   - 例: `fetchItems()` → `fetchItems(filter: String)` への変更

2. **型名変更・リネーム**
   - Entity名、Service名、View名等の変更
   - 例: `ContactEntity` → `FooEntity`

3. **Entity構造変更**
   - プロパティの追加・削除・型変更
   - init、Codable準拠が崩れる変更
   - 例: `FooEntity`に新プロパティ追加 → init全箇所修正必須

4. **明示的な同期変更**
   - 複数ファイルを同時に変更しないと整合性が保てない場合
   - 計画書で明示的に判定

#### 判定基準

「タスクN完了時点でビルドが通る状態を作れるか？」

- **Yes** → 独立タスク（タスクごとにビルド確認）
- **No** → タスクグループ化（グループ完了時にビルド確認）

#### グループ化の前に検討すべき回避策 [MANDATORY]

**原則**: タスクグループ化は**最終手段**。以下の回避策を先に検討すること。

**回避策の優先順位**:

1. **互換レイヤー・Adapter導入**（推奨）
   ```
   例: FooService.fetchItems(filter: String) への変更
   回避策:
   - 旧メソッド fetchItems() を残し、内部で fetchItems(filter: "") を呼ぶ
   - 段階的に呼び出し側を移行
   - 移行完了後に旧メソッド削除

   利点: 各タスクでビルド成功、高速フィードバック維持
   ```

2. **Feature Flag / 条件分岐**
   ```
   例: Entity構造変更
   回避策:
   - Optional プロパティとして追加
   - デフォルト値を設定
   - 段階的に必須化

   利点: ビルド維持、段階的移行
   ```

3. **段階的移行（Deprecation）**
   ```
   例: 型名変更
   回避策:
   - typealias で旧名を残す
   - 段階的に新名に移行
   - 移行完了後に typealias 削除
   ```

**グループ化が避けられないケース**:

回避策を検討した上で、以下の場合のみグループ化を許容:

- Protocol定義の根本的変更（互換性維持不可能）
- 循環参照解消等のアーキテクチャ変更
- パフォーマンス上、互換レイヤーが許容できない

**判定プロセス**:

1. 回避策を検討（上記3つを優先順に）
2. 回避策で対応可能 → 独立タスクで実装
3. 回避策が不可能 → グループ化（理由に「回避策検討結果」を記載）

#### タスクグループの構成

**グループID**: `REFACTOR-XXX`、`GROUP-XXX` 形式（連番）

**タスク表での記載例**:

```markdown

| - | ------ | -------- | ------------- | ---------- | ---------- | ------------ | ------- | -------- | ---- |
| ☐ | 57     | D-001    | FooEntity定義 | タスクごと | -          | ...          | DES-001 | -        | ...  |
```

**グループ化理由**: グループ単位で理由を明記

```markdown

FooServiceのfetchItems()メソッドにfilterパラメータを追加。
呼び出し側3箇所（FooViewModel, BarViewModel, BazViewModel）の同期修正が必須。
Task 1完了時点では呼び出し側でコンパイルエラーが発生するため、グループ化。
```

#### タスク表の列定義（更新）

- **ビルド確認**: `タスクごと` | `スキップ` | `グループ完了時`
- **グループID**: タスクグループID（例: `REFACTOR-001 (2/4)`）、独立タスクは `-`

#### グループ内タスクの実行ルール

1. **実行順序**: グループ内タスクは順番に実行（並列実行不可）
2. **ビルド確認タイミング**:
   - グループ途中タスク: ビルド確認スキップ（エラー許容）
   - グループ最終タスク: ビルド確認必須
3. **失敗時の対応** [MANDATORY]

   **失敗の分類**:
   - **想定内のコンパイルエラー**（継続可能）: グループ化の目的であるコンパイルエラー → 次タスクに進む
   - **想定外のエラー**（要対応）: 実装ミス、論理エラー、設計誤り → 判断フローに従う

   **判断フロー**（想定外エラーの場合）:
   - 軽微な実装ミス（5分以内修正可能） → その場で修正、継続
   - 中程度のエラー（設計は正しい） → 該当タスクのみ再計画、グループ継続
   - 設計誤り（グループ前提が崩壊） → グループ全体を再計画

   **停止判断**: グループ途中タスクで2回連続失敗 → グループ全体を停止、人間に報告

4. **レビュー**: グループ最終タスク完了後に一括レビュー

#### タスクグループの利点

- ✅ リファクタリングが実行可能になる
- ✅ 複雑な変更を段階的に実施できる
- ✅ 各タスクの変更内容が明確（レビュー可能）
- ✅ 影響範囲が計画段階で明確化

#### 注意事項

- グループサイズは**最大10タスク程度**に抑える（大きすぎる場合は分割を検討）
- グループ化の判断は計画書作成時に慎重に行う（不要なグループ化は避ける）
- グループIDは計画書内で一意にする

#### グループサイズ上限超過時の対応 [MANDATORY]

**上限**: 最大10タスク

**超過した場合の対応手順**:

1. **分割可能性の検討**
   - グループを2つ以上に分割できるか確認
   - 例: 50箇所の修正 → 5グループ × 10タスクに分割

2. **暫定API/ブリッジ実装の検討**
   ```
   例: 型名変更で50箇所修正が必要
   対応:
   - Phase 1: typealias + 旧名を使う箇所のみグループ化（10タスク）
   - Phase 2: 残り40箇所を独立タスクで順次移行
   - Phase 3: typealias削除（1タスク）
   ```

3. **段階的リリース戦略**
   - グループ1: コア機能のみ対応（10タスク）
   - リリース・検証
   - グループ2: 残り機能対応（10タスク）

**判断基準**:

- 10タスク超過 → まず回避策を再検討
- 回避策不可能 → 分割・段階的リリース
- それでも不可能 → 設計を見直し（大規模すぎる可能性）

#### グループ内タスクの依存関係 [MANDATORY]

**原則**: グループ内タスクは順次実行のため、依存関係列の記載は**推奨**（必須ではない）

**記載する場合**:

```markdown
| タスクID | 依存関係 |
| -------- | -------- |
| D-010    | -        |
| UI-020   | D-010    |
| UI-021   | D-010    |
| UI-022   | D-010    |
```

**記載しない場合**:

```markdown
| タスクID | 依存関係 |
| -------- | -------- |
| D-010    | -        |
| UI-020   | -        |
| UI-021   | -        |
| UI-022   | -        |
```

**推奨**: オーケストレーターの実装負荷を下げるため、グループ内でも明示的に記載することを推奨。

#### グループ途中タスクの代替検証 [MANDATORY]

**原則**: ビルド確認スキップ中も、可能な限り代替検証を実施する。

**代替検証の優先順位**:

1. **部分コンパイル確認**（最優先）
   - 修正したファイルのみコンパイル
   - 構文エラー、型エラーの早期検出
   - 実施方法: `swiftc -typecheck [修正ファイル].swift`

2. **単体テストの部分実行**（可能な場合）
   - 修正モジュールに閉じたテストのみ実行
   - 実施方法: `swift test --filter FooServiceTests`

3. **静的解析**
   - SwiftLintでコーディング規約違反を検出
   - 実施方法: `swiftlint lint [修正ファイル]`

4. **コードレビュー**（目視確認）
   - 想定内のコンパイルエラーと想定外のエラーを区別
   - 上記1-3が環境制約で実施不可能な場合の最終手段

**注**: iOS/Xcodeプロジェクト構成では `swiftc -typecheck` や `swift test` がモジュール依存やフレームワークimportの影響で正常動作しない場合がある。その場合はコードレビューを代替とする。

**executor への指示形式**:

```markdown
## 検証要件

- ビルド確認: スキップ
- 部分コンパイル確認: 推奨（可能な場合）
- 単体テスト部分実行: 推奨（可能な場合）
- スキップ理由: タスクグループ途中（REFACTOR-001: 2/4）
```

**報告フォーマット**:

```markdown
### 検証結果

- ビルド確認: スキップ
  - 理由: タスクグループ途中（REFACTOR-001: 2/4）
- 代替検証: 部分コンパイル確認
  - 結果: 構文エラーなし
  - 想定内コンパイルエラー: FooViewModel.swift:125（fetchItems呼び出し）
```

#### タスク各列の説明

- **✓**: ✅完了、☐未完了
- **優先度**: 0〜99（大きいほど優先、0は完了済みを示す）
- **タスクID**: 層略称-連番（D-xxx、UI-xxx、I-xxx等）
- **タイトル**: Agent実行単位の名前
- **ビルド確認**: `タスクごと` | `スキップ` | `グループ完了時`（タスクグループの場合のみ使用、独立タスクは省略可能でデフォルト「タスクごと」）
- **グループID**: タスクグループID（例: `REFACTOR-001 (2/4)`）、独立タスクは `-`
- **やるべき内容**: 設計書の該当箇所を特定できるレベルで記載（`<br>`で改行、項目数制限なし）
  - **注意**: プロパティ名・型・メソッドシグネチャ等の実装詳細は**設計書の責務**。計画書には書かない
- **特筆事項**: 実装時の注意点や補足情報（`<br>`で改行、"-"で特になし）
- **設計ID**: 対応する設計ID（`<br>`で改行）
- **依存関係**: 先行タスクID（カンマ区切り、"-"で依存なし）
- **必読**: 実装前に必ず読むべきドキュメント（具体的なファイルパス、`<br>`で改行、"-"で特になし）
- **完了日**: YYYY-MM-DD形式

#### 「必読」列の仕様 [MANDATORY]

**記載形式**: 具体的なファイルパス（プロジェクトルートからの相対パス）

**正しい例**:

- `specs/main/design/DES-001_foo_list_design.md`
- `rules/layer/domain/domain_core.md`

**誤った例**:

- `foo_list_design` ❌（曖昧名）
- `specs/*/design/*.md` ❌（glob禁止）
- `DES-001` ❌（IDのみ）

**理由**: オーケストレーターがexecutorに渡す際、曖昧さを排除するため。

**例外**:

- 「必読」列が `-` の場合は、必読文書なし
- オーケストレーターが実行時に必読文書を特定する（advisor Subagent使用）

#### 設計書が存在しない場合の扱い [MANDATORY]

**ケース**: 単発バグ修正等で設計書を作成しない場合

**設計ID欄の記載**:

- **値**: `-`（設計書なし）
- **要件トレーサビリティマトリクス**: 該当要件の設計ID列に `-` を記載
- **タスク一覧**: 該当タスクの設計ID列に `-` を記載

**例**:

```markdown
## 要件トレーサビリティマトリクス

| ✓  | 要件ID  | タイトル           | 内容 | 設計ID |
| -- | ------- | ------------------ | ---- | ------ |
| ✅ | BUG-001 | データ読み込み失敗 | ...  | -      |

## タスク一覧

| ✓ | 優先度 | タスクID | ビルド確認 | グループID | 設計ID | ... |
| - | ------ | -------- | ---------- | ---------- | ------ | --- |
| ☐ | 99     | FIX-001  | タスクごと | -          | -      | ... |
```

**「全設計書を網羅」の解釈**:

- 設計書が存在する場合は全て網羅
- 設計書を作成しない場合（単発バグ修正等）は `-` で明示

### 用語解説

以下のデザインパターンおよび専門用語の説明：

- **Adapter（アダプター）**: 既存のクラスやフレームワーク（例：外部API）を、アプリ内部のインターフェースに適合させる設計パターン。外部システムとの接続部分。
- **Agent（エージェント）**: UIの振る舞いを自動制御するコンポーネント。例：ActionAgentはユーザー入力時のアクション判定を自動化。
- **Factory（ファクトリ）**: オブジェクトの生成を管理する設計パターン。依存性注入（DI）の基盤となる。
- **Mock（モック）**: テスト用の模擬実装。実際の処理の代わりにダミーデータを返す。
- **Repository（リポジトリ）**: データアクセスを抽象化する層。Domain層がInfrastructure層の詳細を知らずにデータ操作できる。
- **DataStore（データストア）**: データの永続化を担当する層。UserDefaults、CoreData等を使用。
- **Migration（マイグレーション）**: データベースやストレージの構造変更処理。アプリ更新時のデータ移行。
- **DesignToken（デザイントークン）**: デザインシステムの最小単位。色、フォント、間隔等の定数。
- **ViewModifier**: SwiftUIでViewの見た目や動作を変更する修飾子。
- **Converter（コンバーター）**: データ形式を変換する処理。EntityとDTO（Data Transfer Object）の相互変換等。

## 注意事項

1. **要件IDの不変性**: 一度付与した要件IDは変更しない
2. **削除時の扱い**: 要件が削除されても、IDは欠番として残す
3. **追加時の採番**: 新規要件は必ず最後の番号の次を使用
4. **カテゴリの厳守**: ディレクトリ構造とIDプレフィックスを必ず一致させる
5. **APP-001の特殊性**: アプリケーション全体概要は常にAPP-001として固定、設計書は不要
