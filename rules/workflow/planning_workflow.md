# 計画書作成ワークフロー

## 必読文書 [MANDATORY]

**NEVER skip.** 下記を全て読み込み、深く理解すること

- `rules/format/plan_format.md` - 計画書フォーマット定義
- `rules/format/spec_format.md` - ディレクトリ構造・ID体系

**重要**: 計画書は１ファイル作成した時点で人間のレビューを受けること。

**`specs/{feature}/plan/` に計画書を作成します**
**フォーマットはマークダウンファイルです**

## 0. プロジェクト文書構造

### ディレクトリ構成

Feature-based 構造でプロジェクト文書を管理します。

```
specs/
└── {feature}/          # Feature単位（main, csv_import等）
    ├── requirements/   # 要件定義書
    ├── design/         # 設計書
    └── plan/           # 計画書
```

**詳細なディレクトリ構造とID体系**: `rules/format/spec_format.md` を参照

### ファイル命名規則

#### 要件定義書

- **形式**: `{ID}_{機能名}_spec.md`
- **例**: `SCR-001_foo_list_screen_spec.md`

#### 設計書

- **形式**: `DES-XXX_{機能名}_design.md`
- **例**: `DES-001_foo_list_design.md`

#### 計画書

- **形式**: `{feature}_plan.md`
- **例**: `main_plan.md`（Feature名=mainの場合）、`csv_import_plan.md`（Feature名=csv_importの場合）

### 文書間の関係性

```
要件定義書 ←→ 設計書 ←→ タスク
    ↓           ↓         ↓
要件トレーサ  設計トレーサ  実装
ビリティ      ビリティ
マトリクス    マトリクス
```

### 開発フロー

1. **要件定義**: 要件定義書作成（要件ID付与）
2. **設計**: 設計書作成（設計ID付与、要件IDとの紐付け）
3. **計画**: タスク定義（設計IDとの紐付け）
4. **実装**: タスク実行（設計書に基づく実装）

### 文書更新ルール

- **新機能追加時**: 要件定義書 → 設計書 → 計画書の順で作成/更新
- **バグ修正時**:
  - 単発: 直接タスク化（設計書不要）
  - 複数タスク: 設計書作成必須
- **設計変更時**: 設計書更新 → 計画書のマトリクス更新

### ワークフロー開始時の状況確認

ワークフロー開始時に、Featureディレクトリを自動確認して状況を判定する：

| 確認対象                                              | 判定結果                 |
| ----------------------------------------------------- | ------------------------ |
| `specs/{feature}/plan/{feature}_plan.md` が存在する   | 既存計画の更新           |
| `specs/{feature}/plan/{feature}_plan.md` が存在しない | 新規計画作成             |
| `specs/{feature}/design/` に設計書が存在する          | 設計完了、計画書作成可能 |
| `specs/{feature}/design/` に設計書が存在しない        | 設計書作成から開始       |

**運用**: 状況を自動判定し、ユーザーに報告する。選択肢の提示は不要。

## 1. 開発ルール文書、要件定義書、設計書の取得

- 開発ルール文書（rules/**/*.md）は rules-advisor Subagent を使って特定する
- 要件定義書・設計書は specs-advisor Subagent を使って特定する
- **Subagent失敗時**: エラー内容をユーザーに報告し、指示を待つ

## 2.1 バグ修正/新機能追加/リファクタリング

バグ修正/新機能追加/リファクタリングの場合は、通常 `specs/{feature}/plan/{feature}_plan.md` が存在します。
存在しない場合は「2.2 設計書作成とタスク追加のループ」で新規作成してください。

与えられた要求をタスク化する場合、以下を必ず確認し、実行します

1. **要件定義書への反映確認** - その内容が要件定義書（`specs/{feature}/requirements/**/*.md`）に追記または修正されているか。不足・齟齬がある場合は追記、修正を行う。[MANDATORY]
2. **設計書への反映確認** - 設計変更を伴う場合、設計書（`specs/{feature}/design/**/*.md`）に反映されているか。不足・齟齬がある場合は追記、修正を行う。 [MANDATORY]
3. **計画書にタスクを追加する** - 計画書にタスクを追加する場合は、「2.2 計画書を作成」を参考に行うこと [MANDATORY]

## 2.2 設計書作成とタスク追加のループ [MANDATORY]

### 開発の進め方

**重要**: 全ての要件を一度に設計するのではなく、以下のループで段階的に進めます：

```
1. 優先度の高い要件から設計書を1つ作成（DES-XXX）
   ↓
2. 人間のレビュー・承認を受ける
   ↓
3. 承認された設計書のタスクを計画書（{feature}_plan.md）に追加
   ↓
4. 次の要件の設計書作成に戻る（ステップ1へ）
```

このループを全ての要件がカバーされるまで繰り返します。

### なぜ段階的に進めるのか

- **レビューの質向上**: 1設計書ずつ丁寧にレビュー可能
- **早期実装開始**: 承認済み設計のタスクから順次実装開始可能
- **フィードバック反映**: 先行設計の知見を後続設計に活かせる
- **リスク低減**: 大規模な手戻りを防げる

## 2.3 計画書を作成・更新

- 作成するファイル名は `specs/{feature}/plan/{feature}_plan.md`
- 新しい設計書が承認されるたびに、そのタスクを追加更新

### 計画書の詳細構成 [MANDATORY]

`rules/format/plan_format.md`に従い、以下のセクションで構成：

1. **要件トレーサビリティマトリクス**

```markdown
| ✓  | 要件ID  | タイトル         | 内容                               | 設計ID           |
| -- | ------- | ---------------- | ---------------------------------- | ---------------- |
| ✅ | SCR-001 | アイテム一覧画面 | メイン画面、カテゴリサイドバー付き | DES-001, DES-002 |
| ☐  | FNC-001 | カテゴリ管理     | カテゴリの作成・編集・削除機能     | 設計書作成待ち   |
```

2. **設計トレーサビリティマトリクス**

```markdown
| 設計ID  | タイトル         | 内容                                     | 要件ID           | タスクID                     |
| ------- | ---------------- | ---------------------------------------- | ---------------- | ---------------------------- |
| DES-001 | アイテム一覧設計 | アイテム一覧表示とカテゴリフィルタリング | SCR-001, CMP-001 | D-001～D-008, UI-001～UI-005 |
| DES-003 | カテゴリ管理設計 | カテゴリCRUD操作とアイテム移動           | FNC-001, FNC-002 | D-014～D-018, UI-012～UI-018 |
```

3. **タスク一覧（層ごとの表形式）**

```markdown
### Domain層タスク

| ✓ | 優先度 | タスクID | タイトル       | ビルド確認 | グループID | やるべき内容                                                                                                   | 特筆事項 | 設計ID  | 依存関係 | 必読                                         | 完了日 |
| - | ------ | -------- | -------------- | ---------- | ---------- | -------------------------------------------------------------------------------------------------------------- | -------- | ------- | -------- | -------------------------------------------- | ------ |
| ☐ | 55     | D-001    | FooService実装 | タスクごと | -          | ・Actor-basedサービス実装<br>・アイテムCRUD操作<br>・権限管理機能<br>・FooDataStore連携<br>・FooRepository連携 | -        | DES-001 | -        | specs/main/design/DES-001_foo_list_design.md | -      |
```

**注**: 上記は独立タスクの例。タスクグループの例は後述の「5. タスクグループ化の判定」セクション参照。

**「やるべき内容」の記載原則** [MANDATORY]:

設計書を参照すればわかる実装詳細（プロパティ名、型、メソッドシグネチャ等）は計画書に書かない。
設計書の該当セクションを特定できるレベルの記述にとどめること（`plan_format.md` sec「タスク各列の説明」参照）。計画書に実装詳細を転記すると設計書との二重管理になり、不整合の原因となる。

4. **改定履歴**

### タスク作成の詳細手順 [MANDATORY]

#### 1. タスクの抽出方法

設計書から以下の順序でタスクを抽出：

1. **Entity/Enum定義タスク** - 設計書のDomain層セクションから抽出
2. **Protocol定義タスク** - DataStore/Repository Protocolの定義
3. **Service実装タスク** - ビジネスロジックの実装
4. **View/ViewModel実装タスク** - 設計書のUI層セクションから抽出
5. **Infrastructure実装タスク** - DataStore/Repository実装

#### 2. タスクID採番ルール

- **Domain層**: D-001, D-002, D-003...
- **UI層**: UI-001, UI-002, UI-003...
- **Infrastructure層**: I-001, I-002, I-003...
- **DI層**: DI-001, DI-002...
- **修正タスク**: FIX-001, FIX-002...

#### 3. 優先度設定基準

`rules/format/plan_format.md`のタスク分割表を参照：

- **90-99**: 緊急修正（バグ修正、パフォーマンス改善）
- **50-59**: Domain層（Entity、Service、Protocol）
- **30-39**: UI層（View、ViewModel、Component）
- **40-49**: Infrastructure層（DataStoreImpl、RepositoryImpl）
- **25-29**: DI層（Factory登録）

#### 4. task-executor実行を前提とした計画作成 [MANDATORY]

- **1タスク1Agent実行の原則**: 各タスクは1回のAgent実行で完結する単位
- **ビルド・テスト成功必須**: タスク完了時にビルド・テストが成功する規模
- **依存関係の明確化**: 先行タスクをタスクIDで明記
- **並列実行可能なタスク識別**: 依存関係がないタスクは並列実行可能

#### 実装順序の決定基準

1. **共通コンポーネント優先**: 複数画面で使用されるコンポーネントから実装
2. **依存関係考慮**: 依存される側から実装（MainTabView → 各Tab画面）
3. **機能の重要度**: コア機能の画面を優先
4. **開発効率**: 簡単な画面で実装パターンを確立してから複雑な画面へ

#### 依存関係マップの作成（計画作成プロセス用）

**注**: 依存関係マップは**計画作成プロセス中の思考整理用**であり、計画書には記載しない（計画書は4セクション構成、`plan_format.md` 参照）。タスク間の依存関係はタスク表の「依存関係」列に反映する。

```markdown
#### UIコンポーネント依存関係図（作業メモ）

- 基本コンポーネント
  - Button系 (PrimaryButton, SecondaryButton)
  - Input系 (TextField, TextArea)
  - Display系 (Label, Badge)
- 中間コンポーネント
  - ListItem系 (FooListItem, BarListItem)
  - Card系 (InfoCard, DetailCard)
- 複合コンポーネント
  - List系 (FooListView, BarListView)
  - Form系 (FooFormView, SettingsFormView)
```

※ 循環依存が発生しないよう確認すること
※ この図は計画書に含めず、タスク表の「依存関係」列に落とし込む

#### 5. タスクグループ化の判定 [MANDATORY]

各タスクについて、グループ化が必要か判定します。

**判定基準**: 「タスクN完了時点でビルドが通る状態を作れるか？」

- **Yes** → 独立タスク（タスクごとにビルド確認）
- **No** → タスクグループ化（グループ完了時にビルド確認）

**グループ化の典型ケース**: インターフェース変更、型名変更、Entity構造変更など。
ケースの詳細・回避策・記載方法・注意事項は `rules/format/plan_format.md` の「タスクグループ」セクション参照。

**グループ化は最終手段** [MANDATORY]: 回避策（互換レイヤー、Feature Flag、段階的移行）を先に検討すること。

**判定プロセス**（回避策検討後）:

1. タスクの影響範囲を分析（Swift-Selena MCPの`find_type_usages`等を活用）
2. Task完了時点でビルドが通るか確認
3. 通らない場合、影響を受ける全箇所をタスク化
4. 複数タスクをグループ化（`plan_format.md` のグループ記載方法に従う）

#### 確認 [MANDATORY]

- 計画書が、`rules/format/plan_format.md`のフォーマットに従っていることを確認
- **要件トレーサビリティマトリクスが以下を網羅していることを確認**：
  - `specs/{feature}/requirements/*.md` のアプリケーション全体概要（APP-xxx）※直下に配置
  - `specs/{feature}/requirements/screens/**/*.md` の全画面要件（SCR-xxx）
  - `specs/{feature}/requirements/ui_components/**/*.md` の全UIコンポーネント要件（CMP-xxx）
  - `specs/{feature}/requirements/functions/**/*.md` の機能要件（FNC-xxx）
  - `specs/{feature}/requirements/business_logic/**/*.md` のビジネスロジック（BL-xxx）
  - `specs/{feature}/requirements/non_functional/**/*.md` の非機能要件（NF-xxx）
  - `specs/{feature}/requirements/data_models/**/*.md` のデータモデル（DM-xxx）
  - `specs/{feature}/requirements/external_interfaces/**/*.md` の外部インターフェース（EXT-xxx）
  - `specs/{feature}/requirements/navigation/**/*.md` のナビゲーション（NAV-xxx）
  - `specs/{feature}/requirements/theme/**/*.md` のデザイントークン・テーマ（THEME-xxx）
  - `specs/{feature}/requirements/bug_fix/**/*.md` のバグ修正（BUG-xxx）※存在する場合のみ
- **設計トレーサビリティマトリクスが以下を網羅していることを確認**：
  - 全設計書（DES-xxx）のエントリ
  - 各設計書の関連要件ID
  - 各設計書から生成されるタスクID
- **タスク一覧が層ごとの表形式で作成されていることを確認**
- **各タスクに以下が記載されていることを確認**：
  - タスクID（層略称-連番）
  - 優先度（1〜99で初期設定。0は完了済みを示し、オーケストレーターが設定する）
  - やるべき内容（5〜10項目程度を目安）
  - 設計ID（関連する設計書）
  - 依存関係（先行タスクID）
- **タスクの完全性を確認**：
  - 全設計書がタスクに反映されているか
  - タスクの粒度が適切か（1Agent実行で完結）
  - 依存関係に循環がないか
- 計画書の承認を人間に依頼すること

### 2.4 AIレビュー実施 [MANDATORY]

計画書作成/更新時点で、人間レビュー依頼前に `/review` Skill で自動レビュー:

```
/review plan [作成した計画書のファイルパス] --auto-fix
```

🔴致命的問題は自動修正される。結果サマリーが報告された後、次のステップへ進む。

**Skill失敗時**: `/review` が実行できない場合、`plan_format.md` のチェック項目を手動で確認し、人間にレビューを依頼する。

### 2.5 specs_toc.yaml更新について

計画書自体はspecs_toc.yamlの対象外のため、計画書作成のみの場合は更新不要。
要件定義書・設計書を新規作成・更新した場合のみ、`/create-specs-toc` を実行すること。
