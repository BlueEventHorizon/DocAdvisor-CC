# タスク実行ワークフロー（Agent用）

## 必読文書 [MANDATORY]

**NEVER skip.** オーケストレーターから提供される必読文書を全て読み込み、深く理解すること

- 必読文書リストはオーケストレーターがタスク情報として提供する（Step 1 参照）

## 概要

オーケストレーターから与えられたタスク情報に基づいて、1つのタスクを確実に実装する標準手順。

## 重要原則 [MANDATORY]

以下の原則は本ワークフロー全体を通じて**必ず遵守**すること：

### 必須事項

- **1回の実行で1タスクのみ** - 完了後は必ず終了し、次のタスクに進まない
- **オーケストレーターから提供された情報に基づいて実行** - 指定外のタスクへの着手は禁止
- **必読文書は全体を読む** - 部分的な理解ではなく、全体を理解すること
- **実装指示と検証要件に厳密に従う**

### 禁止事項

- 複数タスクの連続実装
- 指定外のタスクへの着手
- 必読文書の読み飛ばし
- {feature}_plan.md の更新（オーケストレーターの責務）
- Subagent の起動、Skill（/コマンド）の実行

## ワークフロー全体像

```
Step 1: タスク情報の受領
    ↓
Step 2: 事前準備（必読文書読み込み、既存コード確認）
    ↓
Step 3: 実装（Domain層はTDD、その他の層は標準手順）
    ↓
Step 4: 検証（ビルド、テスト、動作確認、Code Header）
    ↓
Step 5: 完了処理（結果報告、終了）
```

---

## Step 1: タスク情報の受領 [MANDATORY]

オーケストレーターから以下の情報が提供される（task_orchestration_workflow.md Phase 4.1 に対応）：

| 項目     | 内容                                               |
| -------- | -------------------------------------------------- |
| タスクID | 実装するタスクの識別子                             |
| タスク名 | タスクのタイトル                                   |
| 実装内容 | やるべき内容の詳細リスト                           |
| 必読文書 | 要件定義書、設計書、ルール文書、参照コードのリスト |
| 実装指示 | タスク固有の実装方針                               |
| 検証要件 | ビルド、テスト、動作確認の要否                     |

---

## Step 2: 事前準備

### 2.1 必読文書の読み込み [MANDATORY]

**オーケストレーターから渡された**以下の文書を全文読み込むこと（優先度順）：

1. **設計書**（必須）: タスクの直接根拠。最優先で全文読了
2. **要件定義書**（必須）: 仕様の確認用。関連仕様が離れた場所に記載されている可能性あり
3. **ルール文書**（必須）: レイヤー固有の実装ルール
4. **参照コード**（推奨）: 既存の関連コードを網羅的に確認。量が多い場合は実装に直接関連する部分を優先

### 2.2 既存コード確認 [MANDATORY]

**目的**: 実装に入る前に、関連する既存コードを把握する（読み取り専用フェーズ）。
新規コードの作成・既存コードの修正は Step 3 で行う。

#### Swift-Selena MCP接続時（推奨）

**効率的に実行できること**:

- 類似実装の検索（重複防止）
- ファイル・シンボル定義の特定
- プロトコル準拠・Extension・import依存の確認
- 型の使用箇所・影響範囲の全検索
- 重要な仕様・設計のメモ保存と検索

**使い方**: 最初に`initialize_project`を実行後、各種検索・確認ツールを活用

#### Swift-Selena未接続時

以下のツールで代替する：

- **Grep** — コード内のシンボル検索、パターン検索
- **Glob** — ファイル名パターンでの検索
- **Read** — ファイル内容の読み込み

#### 共通

- Gemini MCP - 技術的不明点調査

## Step 3: 実装

### 3.1 Domain層（TDDサイクル）[MANDATORY]

Domain層Serviceの実装は、以下のTDDサイクルに従う：

#### Red Phase（テスト作成）

1. 期待する振る舞いをテストで記述
2. この時点でコンパイルエラーは許容
3. Mock DataStore/Repositoryの設定を準備

```swift
// 例: テストを先に作成
@Test("データ取得成功時、DataStoreが更新される")
func testFetchSuccess() async throws {
    // 準備
    mockRepository.dataToReturn = [testItem]
    // 実行
    try await service.loadData()
    // 検証
    let items = await mockDataStore.getCurrentItems()
    #expect(items.count == 1)
}
```

#### Green Phase（最小実装）

1. テストが通る最小限のコードを実装
2. 完璧を目指さない、まずテストを通す
3. シンプルな実装を優先

#### Refactor Phase（リファクタリング）

1. テストが通った状態を維持
2. コードの整理、命名改善
3. 重複排除

#### 実装順序

**新規Service実装の場合**:

1. Protocol定義確認
2. **テストケース作成**（先にテスト）
3. Mock準備
4. Service実装（テストが通るまで）
5. リファクタリング
6. 追加テストケース（エッジケース）

**既存Service修正の場合**:

1. **テスト追加**（現在の振る舞いを確認）
2. Service修正
3. テスト確認

### 3.2 その他の層の実装

Domain層以外（UI層、Infrastructure層等）は以下の順序：

1. 必要な場合のみファイル作成（既存ファイル編集を優先）
2. 基本構造の実装
3. 実装内容の各項目を順次実装
4. エラーハンドリング追加
5. コメント追加（日本語）

### 3.3 実装時の確認事項

- オーケストレーターから提供された「実装内容」リストの各項目を1つずつ確実に実装
- 実装指示に従った具体的な実装方針
- **要件定義書に記載されていない重要な仕様がある場合は FAILURE として報告**（executor は人間に直接確認できない）
- 軽微な実装詳細（UI微調整、ログメッセージ等）は設計書やルール文書から推測し、推測した点を報告に記載する
- エラーが発生した場合は Gemini MCP（接続時）で解決策を調査
- 実装方法が不明な場合も同様に Gemini MCP を活用

## Step 4: 検証

オーケストレーターから指定された「検証要件」に従って実施する。

**注**: executorは検証要件の判定ロジックを持たない。オーケストレーターが計画書を読んで判定し、明示的に指定する。

### 4.1 ビルド確認

オーケストレーターから指定された「検証要件」の「ビルド確認」項目に従います。

**「ビルド確認: 必須」の場合**:

`/xcode-build` Skill を実行。

失敗時はFAILURE報告。

**「ビルド確認: スキップ」の場合**:

- ビルド確認を実行しない
- 報告に「ビルド確認: スキップ」を明記
- スキップ理由が提供されている場合は、それも報告に記載

**注**: executorは「なぜスキップするか」を判断しない。オーケストレーターの指示に従うのみ。

### 4.1.5 代替検証（タスクグループ途中タスクの場合）

検証要件で「ビルド確認: スキップ」かつ「部分コンパイル確認: 推奨」の場合:

**実施可能な代替検証**:

1. **部分コンパイル確認**:
   ```bash
   swiftc -typecheck [修正したファイル].swift
   ```
   - 構文エラー、型エラーの検出
   - 想定内エラー（他ファイルとの不整合）は許容

2. **単体テスト部分実行**:
   ```bash
   swift test --filter [修正モジュール]Tests
   ```
   - 修正モジュールに閉じたテストのみ実行

**iOS/Xcodeプロジェクト構成での注意事項**:

- `swiftc -typecheck` はモジュール依存やフレームワークimportにより、単体ファイルでは正常に動作しない場合がある
- `swift test` はSPM構成のテストモジュールにのみ有効。Xcodeプロジェクトのテストは `/xcode-test` Skill を使用
- 上記コマンドでノイズエラー（環境起因のエラー）が多発する場合は、**コードレビューによる目視確認**を代替検証とし、報告にその旨を記載する
- ノイズエラーと実装エラーの区別が困難な場合は、想定外エラーとして報告する（安全側に倒す）

**報告に含める**:

- 実施した代替検証の種類
- 検出されたエラー（想定内/想定外の区別）
- 代替検証が実施不可能だった場合はその理由

### 4.2 テスト実行

検証要件で「テスト実行: 必須」の場合：

`/xcode-test` Skill を実行。

### 4.3 動作確認

検証要件で「動作確認: 必須」の場合：

- UI層: SwiftUI Previewで表示確認
- Infrastructure層: DebugViewで動作確認（存在する場合）

### 4.4 Code Header Format 確認

**Code Header の生成はオーケストレーターが Phase 5 前に `/create-code-headers` Skill で実行する。**
executor は Code Header を手動作成する必要はない。

ただし、既存ファイルの Code Header 内容と実装が乖離していないか確認し、
乖離がある場合は報告に記載すること。

### 4.5 実装完了の確認

以下を確認してから Step 5 に進む：

- [ ] 「実装内容」リストの全項目が実装された
- [ ] 検証要件が「ビルド確認: 必須」の場合 → ビルドが成功した
- [ ] 検証要件が「ビルド確認: スキップ」の場合 → 代替検証を実施した（可能な場合）
- [ ] テストが成功した（Domain層かつテスト実行が指定された場合）

### 4.6 検証失敗時の対応

検証（ビルド/テスト）が失敗した場合：

1. **エラー分析** — エラーメッセージを確認し、原因を特定
2. **修正** — 原因に基づいて修正
3. **再検証** — Step 4.1 から再実行

**再試行上限: 1回**（初回 + 再試行1回 = 最大2回）。2回失敗した場合は修正を中止し、Step 5 で FAILURE として報告する。
自力解決が困難と判断した場合も、残り回数に関わらず FAILURE として報告してよい。

**タスクグループ途中タスクの場合の特例**:

グループ途中タスクでコンパイルエラーが発生した場合、以下で判定:

1. **想定内のエラーか確認**
   - グループ化理由で説明されているエラー（例: インターフェース変更による呼び出し側エラー）
   - 想定内 → SUCCESS報告（エラー内容を補足情報に記載）

2. **想定外のエラー**
   - 実装ミス、論理エラー、設計誤り
   - 想定外 → 修正試行、2回失敗でFAILURE報告

## Step 5: 完了処理 [MANDATORY]

### 5.1 報告

`.claude/agents/task-executor.md` の「出力」セクションに定義されたフォーマットで実行結果を報告する。

必ず **ステータス**（SUCCESS | FAILURE）を明記すること。

> 注: {feature}_plan.md の更新は executor の責務ではない。オーケストレーターがレビュー完了後に更新する。

**検証結果の報告**:

- 実施した検証項目とその結果を記載
- スキップした項目がある場合、スキップ理由を記載（オーケストレーターから提供された理由をそのまま転記）

**報告例（ビルド確認スキップの場合）**:

```markdown
## タスク実行結果

**ステータス**: SUCCESS

**タスクID**: D-010
**タイトル**: FooService.fetch()シグネチャ変更

### 実装内容

- fetchItems()にfilterパラメータを追加
- 型定義を更新

### 検証結果

- ビルド確認: スキップ
  - 理由: タスクグループ途中（REFACTOR-001: 2/4）
- テスト実行: スキップ
- 動作確認: スキップ

### 補足情報

このタスク完了時点で、以下の箇所でコンパイルエラーが発生している可能性があります:

- App/ViewModel/FooViewModel.swift（fetchItems()呼び出し箇所）
- App/ViewModel/BarViewModel.swift（fetchItems()呼び出し箇所）

これは想定内のエラーであり、グループ内の後続タスクで修正されます。
```

**注**: executorは「グループID」や「グループ内位置」を自分で判断しない。オーケストレーターから渡された「スキップ理由」をそのまま報告に転記する。

**報告後、必ず処理を終了する。次のタスクに進まない。**

## 付録

### A. タスクの粒度

各タスクは以下の単位で定義されている：

- 1つのService実装
- 1つのView/ViewModelペア実装
- 1つのDataStore/Repository実装
- 1つのEntity/Enum定義

### B. トラブルシューティング

#### 依存タスクが未完了の場合

- FAILURE として報告し、オーケストレーターに判断を仰ぐ
- 自己判断で依存タスクの実装に着手しない

#### ビルドエラーの場合

1. エラーメッセージを確認
2. Gemini MCP（接続時）で解決策を調査
3. 修正後、再度ビルド確認
4. 2回失敗したら FAILURE として報告

#### 要件が不明確な場合

1. 要件定義書を再確認
2. 関連する他の要件定義書も確認（離れた場所に記載の可能性）
3. 設計書があれば参照
4. それでも不明な場合:
   - 重要な仕様（ビジネスロジック、データモデル等）→ FAILURE として報告
   - 軽微な詳細 → 推測して実装し、報告に推測した旨を記載

#### 必読文書の発見方法

オーケストレーターから「必読文書」として渡されたリストを参照すること。
